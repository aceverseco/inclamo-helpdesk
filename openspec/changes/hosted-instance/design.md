## Context

See proposal.md. What exists today, and what was checked in Chatwoot v4.19.1 (`build/chatwoot`, `VERSION_CW` 4.19.1, Rails 7.2.3.1 by `Gemfile.lock:720`):

- **Our stack is a development one.** `dev/docker-compose.yaml` runs the image with `env_file: .env` from the checkout; `dev/docker-compose.mount.yaml` mounts `custom/` and the two loader files into the official image; `dev/docker-compose.e2e.yaml` sends every Shopify request through a test proxy and says itself it is never for real customers. `dev/env.example` lists the Rails secret, the three Active Record encryption keys (the store connection is refused without them) and the Postgres and Redis passwords.
- **The image is built but not published.** `scripts/build-image.sh` builds `inclamo-helpdesk:<overlay>-cw<chatwoot>` from the assembled tree with Chatwoot's own Dockerfile; `.github/workflows/image.yml` builds it on `main` and checks that it carries the overlay and no `enterprise/`, with `push: false`. A full build takes about half an hour in CI, 5 to 18 minutes on the stand.
- **Lesson from the stand (2026-11-06):** `dev/.env` existed only on the machine, inside the synced tree; one `rsync --delete` removed it while the containers ran, and it was rebuilt from `docker inspect`. Losing the three encryption keys would have made every stored store credential unreadable.
- **Database preparation.** `db:chatwoot_prepare` (`lib/tasks/db_enhancements.rake:17-30`) loads the schema and the seeds on an empty database, then migrates; on an existing one it only migrates. The overlay's rake file (`custom/lib/tasks/inclamo_db.rake`) hooks the same task, so one command brings Chatwoot's and the overlay's tables up to date. The entry point (`docker/entrypoints/rails.sh`) only waits for Postgres; it runs no migration. The schema needs the `vector` extension (`db/schema.rb:19`), hence the pgvector image.
- **First run.** The seeds set the onboarding flag in Redis (`db/seeds.rb:8`); while it is set the dashboard redirects to `/installation/onboarding` (`app/controllers/dashboard_controller.rb:60`), whose `create` builds the first account and a super admin (`app/controllers/installation/onboarding_controller.rb:8-15`) and deletes the flag (`:29-30`). With the "subscribe to updates" box ticked it calls `ChatwootHub.register_instance` with the company, the owner's name and email (`:33`, `lib/chatwoot_hub.rb:99-101`). Sign-up is governed by `ENABLE_ACCOUNT_SIGNUP` (`.env.example:44`).
- **Mail.** `config/initializers/mailer.rb:14-31` builds the SMTP settings from `SMTP_ADDRESS`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_AUTHENTICATION`, `SMTP_DOMAIN`, `SMTP_ENABLE_STARTTLS_AUTO`, `SMTP_OPENSSL_VERIFY_MODE`, `SMTP_SSL`, `SMTP_TLS` and the timeouts; with `SMTP_ADDRESS` blank it switches to `sendmail` (`:34`), which the image does not carry, so mail would be lost without a word. The sender is `MAILER_SENDER_EMAIL` (`.env.example:106`); links use `FRONTEND_URL` (`mailer.rb:7`, `config/environments/production.rb:105`).
- **Attachments.** `config.active_storage.service` is `ACTIVE_STORAGE_SERVICE`, default `local` (`production.rb:43`); `local` keeps files under `storage/` (`config/storage.yml:5-7`, the `storage` volume in our compose), `s3_compatible` takes `STORAGE_BUCKET_NAME`, `STORAGE_ACCESS_KEY_ID`, `STORAGE_SECRET_ACCESS_KEY`, `STORAGE_REGION`, `STORAGE_ENDPOINT`, `STORAGE_FORCE_PATH_STYLE` (`storage.yml:33-40`).
- **TLS.** `FORCE_SSL` (`production.rb:46`, default false).
- **Chatwoot's hub.** `ChatwootHub.instance_config` (`lib/chatwoot_hub.rb:59-67`) is the installation identifier, version, host name taken from `FRONTEND_URL`, environment and edition. `sync_with_hub` (`:85-96`) posts it every day, with counts of accounts, users, inboxes, conversations and messages unless `DISABLE_TELEMETRY` is set (`:88`): `config/schedule.yml:12-15` runs `Internal::TriggerDailyScheduledItemsJob`, which schedules `Internal::CheckNewVersionsJob` in production. `DISABLE_TELEMETRY` therefore removes the counts, not the daily request. `emit_event` stops on `DISABLE_TELEMETRY` (`:122`). Mobile push goes through the hub unless Firebase credentials are configured or `ENABLE_PUSH_RELAY_SERVER` is false (`app/services/notification/push_notification_service.rb:102-115`); browser push (`:66`) does not use the hub.
- **Health.** `GET /api` (`app/controllers/api_controller.rb`) reports `queue_services` by a Redis ping and `data_services` by `ActiveRecord::Base.connection.active?` (`:20-21`). On the development stand on 2026-11-07 it answered `data_services: failing` while the database served sign-ins. Our reading: Rails 7.2 connects lazily, so `active?` is false on a connection that has not run a query yet. Either way the field cannot drive an alarm.
- **Chatwoot's own production compose** (`docker-compose.production.yaml`) uses `pgvector/pgvector:pg16` and `redis:alpine` and publishes Postgres and Redis on `127.0.0.1`.

## Goals / Non-Goals

**Goals:** an instance that a merchant's data can live on, where losing the machine costs at most a day and an hour of work; nothing secret in the repository, the output or the logs; every failure that would be silent (mail, backups, a bad upgrade) made loud; one install that a self-hosting merchant can use as well.

**Non-Goals:** several machines, a managed database, point-in-time recovery, zero-downtime upgrades, Postgres major-version upgrades, the upstream-release routine, our setup wizard.

## Decisions

**D1. `deploy/` is separate from `dev/`.** A production compose file of its own (`deploy/docker-compose.yaml`) with `rails`, `sidekiq`, `postgres`, `redis` and `caddy`; nothing of `dev/` is layered on it, so the source mount and the Shopify test proxy cannot reach a production instance by an extra `-f`. Alternative rejected: one compose file with profiles; one wrong flag would mount the source on a merchant's instance.

**D2. The instance pulls a published image, pinned by tag and digest.** On a tag `v*` the image workflow pushes `<overlay>-cw<chatwoot>` to the registry (assumption 1); `deploy/.env` names `HELPDESK_IMAGE=<registry>/<name>:<tag>@sha256:<digest>`. Postgres is pinned to an exact pgvector tag on Postgres 16, Redis to an exact tag. Alternative rejected: building on the machine, which needs the repository and build tools on a production machine, takes minutes per upgrade and gives no guarantee that two instances run the same bytes.

**D3. Secrets are made once, outside any synced tree.** `deploy/install.sh` writes `/etc/inclamo-helpdesk/helpdesk.env` with `umask 077`, root only, the values drawn from `/dev/urandom` as `e2e/run.sh` already does, and stops when the file exists. The compose file reads it by an absolute path, so no checkout or sync of the repository can delete it. The install never echoes a value; the scripts run with tracing off; the test of the install greps its output and the container logs for each generated value.

**D4. Domain check, then automatic TLS.** Before Caddy starts, the install resolves the domain and compares it with the machine's public addresses; a mismatch stops it, so no certificate request is wasted against the authority's rate limits. Caddy obtains and renews the certificate itself and redirects HTTP to HTTPS; `FORCE_SSL=true` and `FRONTEND_URL=https://<domain>` in the environment. Only Caddy publishes ports. Docker's published ports bypass a host firewall, so the database and Redis must not be published at all, not even on `127.0.0.1`, unlike Chatwoot's own production file.

**D5. First run is Chatwoot's onboarding.** The install runs `db:chatwoot_prepare` once on the empty database (seeds included, so the onboarding flag is set) before `rails` and `sidekiq` start, and never from both containers at once. `ENABLE_ACCOUNT_SIGNUP=false`. Redis runs with append-only persistence, so a restart between install and onboarding does not drop the flag and leave an instance with no administrator. Our setup wizard (slice 7) later replaces this screen.

**D6. Mail must work before the install finishes.** The install requires `SMTP_ADDRESS` and `MAILER_SENDER_EMAIL`, and sends a test message through the stack (`rails runner` with Action Mailer) to an address the operator gives; a refusal stops the install with the server's answer. This closes the silent `sendmail` fallback of `mailer.rb:34`.

**D7. Attachments by `ACTIVE_STORAGE_SERVICE`.** With assumption 2, `s3_compatible` with the `STORAGE_*` variables and a versioned bucket; the nightly backup then carries the database and the environment file, and the bucket's versions carry deleted files. Without it, `local` on the `storage` volume, and the nightly backup carries that volume too. The spec holds for both; the install test runs both.

**D8. The hub hears nothing.** `DISABLE_TELEMETRY=true` and `ENABLE_PUSH_RELAY_SERVER=false` in the environment; the overlay prepends `ChatwootHub` so that `sync_with_hub`, `register_instance` and `emit_event` return without a request. The prepend is overlay code under 0061, not a core patch. A backend spec with network access blocked runs the daily job and onboarding with the box ticked and expects no request. What we give up: the super-admin console's "new version" notice (we track releases ourselves) and mobile push without our own Firebase credentials (assumption 6).

**D9. Backups run on the host, encrypted to a key that is not there.** A systemd timer runs `deploy/backup.sh` nightly: `pg_dump -Fc` through `docker compose exec postgres`, a tar of the `storage` volume when it is used, the environment file; each encrypted with `age` to the public key in `BACKUP_AGE_RECIPIENT` and uploaded to the S3-compatible target with a client running in a container; then the retention of assumption 4 by listing and deleting; then a status file (`/var/lib/inclamo-helpdesk/backup-status.json`, last success and last restore test, mounted read-only into `rails`). A failure posts to `ALERT_WEBHOOK_URL` at once. The private key never touches the machine (assumption 5). Alternative rejected: plain dumps in a private bucket; the dump holds every customer's messages and the bucket's credentials sit on the machine.

**D10. Restore and the restore test.** `deploy/restore.sh` asks for the `age` identity file and stops when it is missing; on an empty installation it decrypts the environment file into place, starts only Postgres, restores the dump, runs `db:chatwoot_prepare` (an existing schema means migrations only, no seeds, so no onboarding flag), restores the volume when used, and starts the stack. `deploy/restore-test.sh` makes a fresh dump with the same command the backup uses and restores it into a throwaway compose project on the same machine with no published port, then checks by `rails runner` that the users, conversations and attachments counts match the source and that the store connection decrypts and reads the store; it also checks that the objects of the last backup exist on the target with the checksums the backup recorded in the status file. It records success in the status file and removes the project. It runs from `upgrade.sh` and from a monthly timer, so the restore key stays off the machine; the full path (download, decrypt with the key, restore) runs in CI with test keys and on each new machine by hand with the real key.

**D11. Upgrade: backup gate, migrations, health, rollback.** `deploy/upgrade.sh <tag>`: run a backup (stop on failure); pull the new image; stop `rails` and `sidekiq` (intake stops, assumption 7); run `db:chatwoot_prepare` with the new image; start; poll `/inclamo/health` for five minutes. On failure: stop, restore the pre-upgrade dump, set the previous image back, start, post the alarm naming the tag. Alternative rejected: rolling migrations back. Chatwoot's migrations are not all reversible, and the overlay's rollback (`inclamo:db:rollback`) covers our tables only.

**D12. Our own health endpoint.** `GET /inclamo/health`, the overlay's first route outside the account routes (`custom/config/routes.rb` says today that everything lives under `/api/v1/accounts/:account_id/inclamo/`; the comment changes). No authentication, no counts, no merchant data. Checks: `SELECT 1`; Redis `PING`; at least one Sidekiq process alive with a recent beat (Sidekiq's process set); backup under 26 hours and restore test under 35 days from the status file; free space on the volume the database lives on over 15 %. Answer 200 or 503 with the failing check names, and the overlay and Chatwoot versions. `/api` stays as Chatwoot made it.

**D13. Alarm from outside.** A monitor outside the machine (assumption 8) requests the health page every minute and posts to the operator's chat after three failures; the machine itself posts backup and upgrade failures. An alarm that lives only on the machine dies with it.

**D14. Machine baseline as a script and a checklist.** `deploy/harden.sh`: the firewall allows 22, 80, 443; `sshd` with `PasswordAuthentication no` and `PermitRootLogin no`; unattended security upgrades; Docker's `json-file` log driver with `max-size` and `max-file` in `daemon.json`. What a CI runner cannot show (password ssh refused, ports seen from the internet) is in the checklist of `docs/install.md`, run on each new machine.

**D15. Tests.** A workflow `install.yml` (on `main`, on tags and by hand) runs `deploy/install.sh` on the runner in a test mode that changes only what a runner cannot have: Caddy's internal authority instead of a public certificate, a fake public address for the domain check, a MinIO container as the S3 target, Mailpit as the SMTP server, a small receiver for the alarm webhook. `e2e/tests/instance-installation.spec.mjs` names one test per scenario and drives the stack through Playwright and shell steps; the upgrade tests go from the previous release tag to the image under test, and to a deliberately broken image. The coverage check maps `instance-installation` to that file; two scenarios go to its exception list with where they are covered, "Password login refused" and "Alarm after three failures", both by the checklist on each new machine.

## Risks / Trade-offs

- [One machine is one point of failure] → recovery point 24 h, recovery time the length of a restore on a new machine, measured on the first instance and written in `docs/install.md`.
- [A rollback loses what arrived after the backup] → intake is stopped during the upgrade, so the gap is the upgrade's minutes; the alarm says when it happened.
- [The restore key is lost] → the backups are unreadable; the store connection can be made again, the conversations cannot. The founder holds the key and a second copy (assumption 5).
- [The monthly restore test does not decrypt what was uploaded] → it restores the same dump before encryption and checks the upload's checksum; decryption with the real key is exercised by hand on each new machine and with test keys in CI.
- [Docker bypasses the host firewall for published ports] → only Caddy publishes; the install test checks the published ports.
- [Upgrades follow Chatwoot's cadence and its security fixes] → this change gives the mechanism; the routine that decides when is the rest of slice 9.
- [Silencing the hub hides Chatwoot's own "new version" notice] → our release routine is the source of new versions.
- [The CI install takes the image build's half hour] → the workflow reuses the image job's cache and runs on `main`, tags and by hand, not on every push.

## Migration Plan

None for code: everything is new. For the first instance: create the machine and the domain, run `deploy/harden.sh`, `deploy/install.sh`, onboarding, connect the store, run `deploy/restore-test.sh` once by hand and the checklist of `docs/install.md`, and only then give the merchant access. Records of that machine (provider, size, region, names) stay outside this repository.
