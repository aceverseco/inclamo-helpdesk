## Context

See `proposal.md` for motivation and the settled items (action set, native sidebar section, no reuse of Chatwoot's own Shopify integration, a role for order actions). Facts that shape the approach, checked against Chatwoot v4.19.1 and the Shopify Admin GraphQL API 2026-10:

- Chatwoot looks up `Custom::<Class>` modules through `prepend_mod_with` / `include_mod_with` when a `custom/` directory exists (`lib/chatwoot_app.rb`, `config/initializers/01_inject_enterprise_edition_module.rb`). `config/application.rb` adds only `enterprise/` to the load paths, so `custom/` needs an initializer of its own.
- The conversation sidebar is assembled in `app/javascript/dashboard/routes/dashboard/conversation/ContactPanel.vue` as a draggable list of named sections; the default list and order live in `app/javascript/dashboard/composables/useUISettings.js`. There is no hook for adding a section.
- Chatwoot CE has two roles: administrator and agent. Finer roles are a paid-edition feature and are not used.
- Chatwoot's own Shopify integration is invisible unless its account feature flag and the operator's OAuth client are set. It stays off.
- Shopify custom apps: since 1 January 2026 a merchant creates a custom app in the Dev Dashboard, not in the store's admin. Such an app has no static token: the server exchanges the client ID and secret for an access token that lives 24 hours (client credentials grant), which works only when the app and the store belong to the same Shopify organisation. Legacy admin-created apps keep their static `shpat_` tokens.
- Shopify protected customer data, checked live on a development store on 2026-11-05: a Dev Dashboard app with no distribution method chosen is refused the whole `Customer` object (HTTP 200, GraphQL error `ACCESS_DENIED`, "This app is not approved to access the Customer object"), and likewise the `Order` and `DraftOrder` objects. The first check read "orders stay readable" because the store was still empty: the store refuses only when it has an object to return, and answers an empty list otherwise. Once custom distribution is chosen for the app, orders and customers with names and emails are returned. Shopify's documentation states the rule: for custom apps both levels of protected customer data are always available; for legacy apps created in a store's admin, names, emails, phones and addresses vary by the store's plan (the Help Center's "Grow or higher"). So a freshly created app with no distribution method cannot be connected at all, and the limited mode is what a legacy token on a lower plan may get. Not yet checked: an app created by a merchant's own organisation rather than a partner organisation, and a real Basic-plan store.
- Shopify client credentials grant, checked live: the token starts `shpua_`, `expires_in` is 86399; a refused exchange is an HTML page with HTTP 400 whose title carries the reason (`invalid_request` for a wrong secret, `application_cannot_be_found`, `app_not_installed`); an unknown shop is HTTP 404. `currentAppInstallation.accessScopes` lists implied read scopes (`read_orders` next to `write_orders`), the token answer does not.
- Shopify gives an app the last 60 days of orders unless it holds `read_all_orders`; whether a Dev Dashboard custom app can take that scope without review is to be confirmed.
- Shopify: order editing exists (`orderEditBegin` … `orderEditCommit`, scope `write_order_edits`, unfulfilled items only, store-currency orders only).
- Shopify: `orderCancel` needs `write_orders`, takes reason, restock, refund method and notify, and is asynchronous (returns a job). `refundCreate` needs `write_orders` and requires an idempotency key from API version 2026-04. `orderUpdate` with `shippingAddress` needs `write_orders`. `draftOrderCreateFromOrder(orderId)` needs `write_draft_orders` and `write_orders`; `draftOrderUpdate`, `draftOrderComplete` and `draftOrderDelete` need `write_draft_orders`. `draftOrderComplete` turns the draft into a regular order and commits inventory.

## Goals / Non-Goals

**Goals:**
- The whole backend of this change in `custom/`, with no edit to a Chatwoot core Ruby file.
- One seam in the dashboard, generic enough to carry later sections, carried as a patch.
- A store connection that the hosted edition can later satisfy with OAuth without touching the panel.
- No order or customer data at rest in the helpdesk beyond the conversation attributes named in the spec.

**Non-Goals:**
- More than one store per account.
- Shopify webhooks; the panel reads on demand.
- A settings page; the connection form lives in the panel's "not connected" state until the settings slice.
- Order editing (adding or removing line items of an existing order): possible in Shopify, planned for release 0.2, not this change.
- Creating a new order from scratch (catalogue search, custom lines, invoice): planned for release 0.2. This change has only the duplicate as a free replacement.
- Roles finer than one order-actions role (per action, per amount).
- Amount limits for human agents. Limits belong to the AI slice.
- Returns, exchanges, subscriptions, gift cards, store credit.

## Decisions

**D1. Backend as a `custom/` overlay with its own loader, routes and migrations.** Two small files are added to Chatwoot's tree, neither replacing a file of Chatwoot's: `config/initializers/00_inclamo_overlay.rb`, which hands over to `custom/config/overlay.rb`, and `lib/tasks/inclamo_overlay.rake`, which loads `custom/lib/tasks/*.rake` (rake collects tasks before the application initializes, so an initializer cannot register them). `custom/config/overlay.rb` pushes `custom/app/*` and `custom/lib` into the main autoloader, prepends `custom/config/routes.rb` to the route set, adds the overlay's locales and keeps `inclamo_` tables out of Chatwoot's schema dump. Our tables are prefixed `inclamo_`.
- *Migrations are recorded apart from Chatwoot's.* `custom/db/migrate` is run by our own migration context with its own record table, `inclamo_schema_migrations`, hooked after every task with which Chatwoot prepares its database: `db:migrate`, `db:chatwoot_prepare`, `db:setup`, `db:prepare` and `db:test:prepare`. (`db:chatwoot_prepare` on a server without a database runs `db:setup` and never reaches `db:migrate`; the end-to-end run on a fresh stack caught the first installation coming up without the overlay's tables.) Reason, found while building this: a fresh install loads Chatwoot's `schema.rb`, and Rails then marks every known migration older than that schema as already run; in a shared record an overlay migration older than the next Chatwoot release would be marked as run without its table being created. Alternative, appending `custom/db/migrate` to Chatwoot's migration paths: rejected for that reason. Alternative, putting migrations and routes into Chatwoot's own `db/migrate` and `config/routes.rb` as its paid editions do: rejected because every such file is a merge conflict waiting for the next upstream release.
- *Two empty namespaces.* Chatwoot's extension hook walks `Enterprise` and `Custom` whenever `custom/` exists and raises when either is not defined at all (v4.19.1, `false&.const_defined?` in `01_inject_enterprise_edition_module.rb`); upstream never meets this because its `custom/` only exists next to `enterprise/`. The overlay defines both as empty modules.

**D2. Our own API namespace.** `/api/v1/accounts/:account_id/inclamo/shopify/...`: `connection` (show, create, recheck, destroy), `customers` (match, choose), `orders` (list, show, lookup by number), `orders/:id/cancel|refund|address|replacement`, `conversations/:id/order` (mark, clear), `order_roles` (list, give, take). Authentication and account scoping reuse Chatwoot's base controllers by inheritance, not by editing them.

**D3. Connection record behind an interface.** Table `inclamo_shopify_connections`: account (unique), shop domain, auth kind (`client_credentials`, `legacy_token`; `oauth` later for the hosted edition), encrypted client secret and access token, token expiry, scopes, API version, store name, customer-data mode (`full`, `limited`), status (`working`, `broken`), last checked at. The panel and the actions talk to a `StoreConnection` object that hands out a valid token and renews it five minutes before expiry; nothing else sees the credentials. Encryption uses Rails Active Record encryption; Chatwoot treats those keys as optional, so connecting is refused when they are absent (spec: "The token is a secret").

**D4. Verification on connect.** For `client_credentials`, first the token exchange; then one GraphQL call for `shop { name myshopifyDomain plan }` and `currentAppInstallation { accessScopes { handle } }`, and one probe query for one order and one customer. Refused orders mean an app with no distribution method: nothing is saved and the form says so. Refused customers alone mean the limited mode; both given mean `full`. Orders are asked first because the store names only its first refusal. The same sequence serves "check again". An empty store answers the probe whatever the app is, so the panel also recognises the refusal when it reads (state `refused`).

**D5. Shopify Admin GraphQL, version pinned.** Version `2026-10` in one constant; bumping it is part of the upstream-release routine. Throttled answers are retried with the wait Shopify states, within the request's time limit. No REST.

**D6. Read on demand, 60-second cache, nothing at rest.** Orders are fetched by our backend per panel load and cached in Redis for 60 s keyed by account and customer. The only persisted order data are the conversation attributes of the marked order (number, statuses, first tracking number and link, admin link). The chosen customer for an ambiguous match is kept as a contact attribute holding the Shopify customer id.

**D7. Idempotent actions.** The dialog creates an action id when it opens; the backend writes the action record with that id before calling Shopify and passes it as the idempotency key of `refundCreate`. A repeated request with the same id returns the recorded outcome. `orderCancel` is polled for up to 10 s; after that the order is shown as "cancelling" and re-read on the next load. An action whose answer was lost is recorded as `unknown` and resolved by reading the order.

**D8. Record of actions.** Table `inclamo_order_actions`: account, conversation, agent, order id and number, action, parameters without personal data (amounts, reason, flags; never the address), outcome (`accepted`, `refused`, `unknown`), Shopify's message, timestamps. The private note is created through Chatwoot's own message builder as the acting agent, so it appears in the timeline like any note. Chatwoot CE has no audit log; this table is ours.

**D9. One dashboard seam: a registry of sidebar sections.** `ContactPanel.vue` gets one extra branch that renders any section found in a registry, inside the same accordion wrapper as the built-in sections; `useUISettings.js` appends the registry's names to the default order. Our components, store module, API client and locale strings live in a directory of our own and are reached only through the registry file. Two core files touched, both by a few lines. Alternative: a Dashboard App iframe; rejected for this feature (orders and messages must be visible together). The seam stays a patch in `patches/`: decided on 2026-11-06 that nothing is proposed to the Chatwoot repository, neither the registry nor the fix for the namespaces in D1.

**D10. The connection form lives in the panel for now.** Not connected: administrators see "Connect Shopify" in the section, which opens a dialog with the domain, the credentials (client ID and secret, or a legacy token) and the list of scopes to grant. This avoids a second seam (settings navigation) in this slice.

**D11. Own image, built with Chatwoot's own Dockerfile.** `scripts/assemble.sh` produces the build tree: Chatwoot's source at the tag pinned in `custom/CHATWOOT_VERSION`, `enterprise/` removed the same way upstream builds its `-ce` image, the seam patches from `patches/` applied (a patch that does not apply stops the script), then `custom/` and the two loader files copied in. `scripts/build-image.sh` and CI build that tree with `docker/Dockerfile` as it ships in Chatwoot, so the image differs from the official one only by what we add. The same assembled tree is what the backend specs run in. For development, the official `-ce` image runs with `custom/` and the loader files mounted (`dev/docker-compose.mount.yaml`); that path cannot carry dashboard changes.

**D12. Three layers of tests, the top one end to end on a live store.**
- Backend specs run against recorded Shopify answers; every GraphQL document is validated against the published schema of the pinned version. They run on every push.
- End-to-end tests (Playwright, in `e2e/`) drive the real dashboard of our image, started by compose with Postgres and Redis and a seeded account (one administrator, one agent with the order-actions role, one without), connected to a dedicated development store. Every scenario of both specs has an end-to-end test named after it; a scenario without one fails a coverage check in CI.
- Store state for each test is created through the Admin API by a separate seeding app with wider scopes (customers, products, orders), tagged per run and removed afterwards, so the app the helpdesk connects with keeps exactly the scopes the merchant guide asks for.
- Failure scenarios (store does not answer, throttling, lost answer, authentication error) are produced by a proxy between the helpdesk and Shopify that the test controls; the Shopify base URL of the backend is configurable for this only in the test environment.
- A third app with no distribution method stands for the app a merchant forgot to finish: the store really refuses it orders and customers, and the connection is really refused. The limited mode itself (orders given, customers' personal data withheld) cannot be produced on a development store and is exercised by the proxy refusing the customer part of the probe. A real Basic-plan store stays a manual check.
- End-to-end tests run on the main branch, before every release and on demand; credentials of the development store live in CI secrets and are never printed.

**D13. The order-actions role is our own record.** Table `inclamo_order_roles`: account, user, given by, given at; one row means the agent holds the role. Administrators need no row. Every action endpoint checks it on the server before anything else; the panel reads it together with the scopes to decide what to show. Chatwoot's `custom_roles` tables and `custom_role_id` column belong to its paid edition and are not read or written. Alternative: a conversation or agent custom attribute; rejected because any agent could edit it through Chatwoot's API. The list of agents with a switch per agent lives in the panel's administrator menu, next to the connection (same reasoning as D10: no second seam in this slice).

**D14. The free replacement goes through a draft order, and needs `read_products`.** Found while building it, on a live store: the store rebuilds a draft's lines on every update, a line can only be named by its variant (an update that names lines by their own ids is refused with "Merchandise title is empty"), and a variant can only be read with `read_products`. So the replacement needs that scope besides `write_orders` and `write_draft_orders`; the panel itself reads orders without variants and needs no product scope. Alternatives: copying the whole order without letting the agent remove items (drops a requirement), or re-creating the lines as custom items with a title and a price (loses the link to the product and its stock); both rejected. The mechanics: Three steps under one action id: `draftOrderCreateFromOrder` (the store copies items, customer and addresses itself, so the address never passes through us), `draftOrderUpdate` (the items the agent kept, a 100 % order discount, a free shipping line, a tag and a note naming the original order), `draftOrderComplete`. The draft id is written to the action record after step one, so a repeated request continues from the recorded step instead of creating a second draft. When step two or three is refused, the draft is deleted; when the deletion fails, the message names the draft with a link. Alternative: `draftOrderCreate` with lines built by us; rejected because it needs the address and customer on our side and breaks in the limited mode.

**D15. A refund restocks at a location, read with `read_locations`.** Decided on 2026-11-06 and then corrected by a live store on the same day. The first version restocked items that had not shipped without naming a location and left shipped items out; it had only ever run against recorded answers, and a live store refuses it: every restocked line must name a location ("You need to set a location to restock items"), in a store with one location too, shipped or not. What the store takes, each point tried on a development store:
- units that have not shipped go back as a cancellation (`CANCEL`), units that have shipped as a return (`RETURN`), both with a location;
- a unit sent as the wrong kind is accepted and silently not restocked (a return of an unshipped unit is recorded as `NO_RESTOCK`; a cancellation of a shipped unit drops the line from the refund);
- one line may be sent as two entries, so a line that has shipped in part is split: its unshipped units as a cancellation, the rest as a return. Units that have not shipped are counted first.

The location is the store's only active one, or the one the agent chooses in the confirmation when there are several; nothing is preselected among several, so that stock never lands in a warehouse nobody chose. Locations are read when the confirmation is calculated, only when something is to be restocked, and the chosen one is checked against that list again when the refund is made. The store is asked what it would refund without any restocking, because the money does not depend on it. The scope is optional in the same way as the write scopes: without it the refund works, nothing is restocked, and the confirmation names the scope. The location id is kept in the action record; it is not personal data. The checkbox is off by default: a parcel is usually still on its way back when the money is returned.

## Risks / Trade-offs

- [Upstream rewrites `ContactPanel.vue`] → the seam is two small patches; CI catches a failed apply at build time, and the patch is redone for that release.
- [Upstream removes or renames a hook our overlay relies on] → this slice prepends nothing in core classes (own controllers, own tables, Chatwoot's public builders), so its exposure is the base controller and the message builder interfaces; covered by tests on every upstream tag.
- [A wrong refund is money gone] → confirmation with amount and destination, refusal above the refundable, idempotency, action record. No amount limit for humans in this slice is a deliberate non-goal.
- [Token leak] → encrypted at rest, never returned, never logged; connection refused without encryption keys.
- [Shopify throttling on busy accounts] → 60-second cache, cost-aware queries (ten orders per page), stated wait honoured.
- [A store connects in the limited mode because the merchant's app has no access to customer data] → the limited mode keeps lookup by order number, statuses, tracking, cancel and refund working, and tells the administrator why; the notice names what lifts it (an app created in the Dev Dashboard with custom distribution). A legacy admin-created app on a plan that hides names and addresses stays limited until the merchant creates such an app. A Dev Dashboard app with no distribution method is a different case: the store refuses it orders too, so it is not connected, and the form names the missing step.
- [A replacement takes stock and creates a real order] → confirmation states it; the role gates who can do it; the order is tagged and names the original, so the merchant can find every replacement.
- [A half-done replacement leaves a draft behind] → draft id recorded after the first step, delete on failure, named in the message when deletion fails.
- [End-to-end tests depend on a live development store and Shopify's limits] → one dedicated store, data tagged per run and cleaned up, tests serial against the store, backend specs on recorded answers keep every push fast.
- [Something only a real Basic-plan store shows] → one manual check before release, recorded in the design.
- [Personal data] → address and customer details pass through memory and a 60-second cache only; attributes and records are free of them by spec.

## Migration Plan

New tables and a new image; nothing existing changes. Rollback: run the official image, the `inclamo_` tables stay unused. Removing `custom/` returns a stock Chatwoot.

## What the end-to-end runs showed

Recorded here because none of it could be read from documentation (task 10.2). All on a development store, 2026-11-05.

- **A first installation came up without the overlay's tables.** `db:chatwoot_prepare` on a server without a database runs `db:setup` and never `db:migrate`. Fixed in D1; found only because the suite starts a stack from nothing.
- **Chatwoot's first-run page.** Until the flag `CHATWOOT_INSTALLATION_ONBOARDING` is gone from Redis, `/installation/onboarding` lets anyone who reaches the instance create its super administrator. `e2e/setup.rb` removes it; the installer slice must own this for real installations.
- **Orders and customers need a distribution method.** An app with none chosen is refused the `Customer`, `Order` and `DraftOrder` objects; with custom distribution they are given. The three test apps are checked by `e2e/check-apps.mjs`.
- **The store refuses only what exists.** The same app gets an empty list, not a refusal, when a query matches nothing, and `ordersCount` answers either way. An earlier note here said such an app could still read orders; that was read from a store with no orders yet. The third test app showed it: the limited-mode test, run against a real app with no distribution method instead of the proxy, found no order. Hence the refusal at connect, and the `refused` state of the panel for a store that was empty when it was connected.
- **A development store on the Basic plan behaves like the one on Grow.** The whole suite was run against a second development store created with the Basic plan and an app with custom distribution: every scenario passed, with customers' names, emails and addresses given and the free replacement working. This says nothing yet about a paid store, where the plan is billed rather than simulated (task 10.3).
- **The suite brings its own catalogue.** It had silently relied on products that happened to be in the first store. On an empty store it now creates the three products it orders, priced above the amounts the refund tests use.
- **`read_all_orders` is not a scope an app can simply list.** The Dev Dashboard refuses it as invalid. The panel therefore sees 60 days of orders.
- **A draft's lines can only be named by variants**, which need `read_products` (D14).
- **Restocking needs a location, always**, and reading locations needs another scope, `read_locations`. An earlier note here said only shipped items needed one; that was never tried on a store. The store's exact rules are in D15.
- **A draft with a total of zero completes into a paid order.**
- **The store words `read_locations` more widely than it is.** Its consent screen for that one scope lists "Locations" and also "Store owner: phone number, physical address". The helpdesk asks for the id and the name of each location; the guide says so.
- **Shopify's idempotency key holds.** A refund sent twice with the same key, the first answer lost, is one refund in the store.
- **Shipping addresses are checked against the store's markets.** An address in a country the store does not sell to is refused by the store ("Country/region not supported"); the dialog shows that sentence.
- **Limits of the test bed itself:** a development store accepts about five created orders a minute; Chatwoot limits a user's concurrent sessions and throttles sign-ins. The suite paces its seeding, signs each user in once per run and runs with `ENABLE_RACK_ATTACK=false`.
- **To make the store say no, the proxy must answer itself.** Changing the store's real answer afterwards lets the store act: the first version of two refusal tests created a real order and a real refund while the helpdesk reported a refusal.

Not learned yet: which notification, if any, the store sends the customer for a completed replacement; anything about a real Basic-plan store or an app created by a merchant's own organisation.
