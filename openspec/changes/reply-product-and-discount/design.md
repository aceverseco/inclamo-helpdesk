## Context

See proposal.md. `new-order-with-invoice` (commit 23a471a) built the product search (`ProductSearch` in `custom/lib/inclamo/shopify/product_search.rb`, `product_search.graphql`, `ProductSearch.vue`), the runner's order-less path (`OrderAction::ORDER_LESS`, `OrderActionRunner#perform_order_less`, handlers built with `customer:`, the `:unknown` state) and `insertIntoReply(text)` in `shims/.../inclamo/reply.js`. The action runner handles gate, scope, record and private note. The founder's decisions of 2026-11-06 are in proposal.md.

## Goals / Non-Goals

**Goals:** reuse the search, the order-less path and the reply insert; the agent picks, the administrator decides; the reply stays the agent's text, nothing is sent by us.

**Non-Goals:** rich product cards; several products at once; presets limited to products or collections; a minimum order; editing or deleting codes later; reporting on codes used.

## Decisions

**D1. One inserted line per product.** Rich editor: "Title, price" with the title as a Markdown link. Plain-text channels: "Title, price: URL". The link is the product's `onlineStoreUrl`; when it is null the product is marked "not in the online store" in the results and inserted without a link. `ProductSearch.present_product` gains `online_store_url`; `ProductSearch.vue` marks a product without it when given `show-storefront`. Whether an inbox keeps links is read from Chatwoot's own formatting table (`dashboard/constants/editor`), not from the editor, so that the settings page does not load the editor.

**D2. The code is a basic discount** (`discountCodeBasicCreate`, findings below): `customerGets: { value, items: { all: true } }` (off the whole order), the value from the preset (`percentage: value / 100` or `discountAmount: { amount, appliesOnEachItem: false }`), `startsAt` now, `endsAt` now + the preset's days or null, `usageLimit` the preset's uses. Audience "this customer": `context: { customers: { add: [matched customer] } }`, `appliesOncePerCustomer: false` so that the customer may use all the uses. Audience "anyone": `context: { all: ALL }`, `appliesOncePerCustomer: true` (once per buyer). Title "<preset name> · helpdesk conversation <id>".

**D3. The code's text** is `THANKS-` and eight characters from an alphabet without look-alike characters (`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`), made by the runner and not editable. When the store answers `TAKEN` the runner makes a new text and tries again, three attempts in all; any other refusal ends the attempt with the store's reason. The text is written into the record before the store is asked, so a lost answer is settled by `discount_code_by_code`: found means accepted, not found after the attempt means refused.

**D4. Presets.** Table `inclamo_discount_presets`: `account_id`, `name` (1–60), `kind` (`percentage` | `amount`), `value` (decimal; percentage above 0 and at most 100, amount above 0), `expires_in_days` (integer above 0, or null for never), `usage_limit` (integer, 1 or more), `audience` (`customer` | `anyone`); listed in the order they were added. The amount is in the shop's currency, shown with the connection's `shop_currency`. Administrator endpoints list, create, update and delete; agents holding the right may list. A code keeps its own conditions in its record, so changing or deleting a preset changes no code.

**D5. The right to give discounts.** Table `inclamo_discount_grants`, one row per account member, the same shape as `inclamo_order_roles` (`account_user_id` unique with cascade, `granted_by`). `Inclamo::DiscountGrant.allows?(account_user)` is true for administrators and for members with a row. Administrator endpoints give and take it.

**D6. Settings page.** One entry in our settings registry, "Discount codes", for administrators: the list of presets with add, edit and delete, and below it the members with a switch "May give discounts" (administrators shown as always allowed, as on the order-actions page).

**D7. Runner and gating.** `discount` joins `OrderAction::ACTIONS` and `ORDER_LESS`, and `ShopifyConnection::ACTION_SCOPES` with `write_discounts`. The runner's `gate` asks `DiscountGrant.allows?` instead of `OrderRole.allows?` for `discount` (an anchored change in `gate`). The handler's `refusal` refuses `unknown_preset` and, for audience "customer" without a matched customer, `customer_not_found`. The record's params hold the preset id and name, kind, value, expiry date, uses, audience and the code; progress holds the discount's id. No customer name, email or `summary` is recorded.

**D8. Panel and controls.** The panel's connection gains `products_readable` (the catalogue can be searched); its viewer gains `can_give_discounts`; the actions report gains `discount` with its missing scope; the panel's answer gains the presets (id, name, kind, value, expiry, uses, audience) when the agent holds the right. "Insert product" and "Discount code" sit at the top of the Orders section, present also when no customer is matched. "Discount code" is offered when the agent holds the right, the connection has `write_discounts` and a preset exists; an administrator sees a line naming the missing permission, or pointing to the settings page when no preset exists. The dialog lists the presets with their conditions; a "this customer" preset without a matched customer is shown disabled with "Customer not found". Picking one and confirming creates the code and inserts it with `insertIntoReply`.

## Probe findings (task 1.1, 2026-11-06)

Run on the development store with the Bench app holding `write_discounts` (version `inclamo-helpdesk-bench-5`), Admin API 2026-10. Every code the probe made was deleted; none was left.

- **Input shape.** `discountCodeBasicCreate(basicCodeDiscount: DiscountCodeBasicInput!)` with `title`, `code`, `startsAt`, `endsAt`, `usageLimit: 1`, `appliesOncePerCustomer: true`, `customerGets: { value, items: { all: true } }` and `context`. There is no `customerSelection` in this version: the customer goes into `context: { customers: { add: [<customer gid>] } }`, anyone into `context: { all: ALL }`. The input also takes `tags`.
- **Value.** A percentage is a fraction: `{ percentage: 0.1 }` is 10 %; `10` is refused with `VALUE_OUTSIDE_RANGE` ("Value must be between 0.0 and 1.0"). An amount is `{ discountAmount: { amount: "5.00", appliesOnEachItem: false } }` in the shop's currency; there is no currency in the input. With `items: { all: true }` both come back with `discountClasses: [ORDER]`, i.e. off the whole order, and combine with no other discount by default.
- **Expiry.** `endsAt` is kept to the second; `endsAt: null` is a code that never expires. `startsAt` is sent as now.
- **Read back.** `codeDiscountNode(id)` returns `context` as `DiscountCustomers { customers { id } }` or `DiscountBuyerSelectionAll { all }`, and the value as `DiscountPercentage { percentage }` or `DiscountAmount { amount { amount currencyCode } appliesOnEachItem }`. `summary` names the customer, so it is personal data and is not recorded.
- **Duplicate text.** Refused as a user error, `code: TAKEN`, field `["basicCodeDiscount","code"]`, message "Code must be unique. Please try a different code." The check ignores case: the lower-case copy of an existing code is refused the same way.
- **No scope.** An app without `write_discounts` gets HTTP 200 with a top-level error `ACCESS_DENIED`, `extensions.requiredAccess` "Apps must have `write_discounts` access scope.", and `data.discountCodeBasicCreate: null`. Nothing is created.
- **Editor insert (from `new-order-with-invoice` task 1.2, design D3 there).** `emitter.emit(BUS_EVENTS.INSERT_INTO_RICH_EDITOR, text)` from a sidebar component inserts at the cursor and unfolds the reply box; nothing is sent. Widget and email inboxes render Markdown `[title](url)` as a link; the API inbox (plain-text schema) strips a Markdown link to its text, so D1's "Title, price: URL" form is needed there. The text follows the editor's mode: in private-note mode it lands in the note, and no event switches the mode.
- **Storefront link on a password-protected store (2026-11-07).** A product published in the Online Store (`publishedOnPublication: true`) still has `onlineStoreUrl: null` while the store is password-protected, as every development store is; `onlineStorePreviewUrl` holds its future address. So D1 marks every product of a closed store as "not in the online store", which is right: a customer cannot open the link. The end-to-end test "Product with a link" makes the proxy answer as an open store does (patch `storefront`, the preview address); the seed confirms the publication with `publishedOnPublication` (`read_publications`, seeder version `inclamo-helpdesk-seeder-3` with `write_publications`).
- **Finding a run's codes.** `codeDiscountNodes(query: "title:\"<title>\"")` found all three codes right after creation; `tag:<tag>` found none. The end-to-end tests name their presets after the run, so a code's title starts with the run; `title:E2E-<run>*` found such a code on the store (task 1.3), and the seed's clean-up removes them.

## Risks / Trade-offs

- [A preset may be large] → only administrators set presets and only agents given the right use them; every code is recorded with the agent's name.
- [A code tied to a customer needs the customer to be signed in or to use the same email at checkout] → the dialog says the code works for this customer's email only.
- [A code made in private-note mode lands in the note] → the dialog's confirmation says where the text goes; the agent sees it in the editor before sending.
- [The insert event changes in a Chatwoot release] → a component test and an end-to-end test catch it; the fallback is a copy button.
- [Code text collision] → 32^8 texts; a `TAKEN` answer is retried with a new text, three attempts in all.
